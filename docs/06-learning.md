# 第 6 章 研究学习要点（如何检验是否真正掌握）

> [← 返回教程目录](../README.md#教程目录生产级-iot-开发教程)

## 项目一句话概括

> 用 Node.js 实现工业设备数据采集全链路：Modbus 协议读取设备 → MQTT 传输（QoS 1 + 幂等）→ 断线缓存补报 → TDengine 时序存储，支持远程指令下发。

## 可深入展开的技术点（每个都应能独立讲透原理）

1. **MQTT 发布订阅模型与 QoS 语义**（为什么 QoS 1 + 业务幂等是最优组合）
2. **断线缓存补报设计**（先落库再上报、成功才删、平台幂等兜底）
3. **指令下发可靠性**（msgId 配对、超时重试、执行幂等）
4. **时序库选型**（为什么 IoT 用 TDengine 不用 MySQL：列式 + 压缩 + 时间分区 + 超级表）
5. **网关架构**（为什么中间要有 broker：连接解耦、多消费者、平台升级无感）
6. **生产差距认知**（能清晰说出"demo 到生产还差什么"——这是工程判断力的体现）

## 踩坑复盘：一个真实问题的排查与改进

> 遇到过"断网恢复后数据补报压垮平台"的问题——最初网关恢复后全量补报，broker 和数据库瞬间打满。后来加了三级措施：补报限速、随机错峰、缓存容量上限。这件事让我理解了工业场景下"兜底机制本身也需要保护"。

## 自测清单（检验学习成果）

- [ ] 不查代码，能画出完整数据链路图（设备 → 网关 → broker → 平台 → 存储）
- [ ] 能解释 QoS 0/1/2 的区别及各自适用场景
- [ ] 能说出断线缓存补报的完整设计（缓存什么、何时删、何时补、怎么防风暴）
- [ ] 能讲清 MQTT 指令下发的可靠性保障（msgId、ack、超时、幂等）
- [ ] 能解释时序库与关系库的核心差异，以及超级表（STABLE）模型的含义
- [ ] 能指出本仓库代码距离生产还差哪些方面（高可用、安全、可观测、运维）
