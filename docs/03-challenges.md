# 第 3 章 难点清单与应对策略（核心章节）

> [← 返回教程目录](../README.md#教程目录生产级-iot-开发教程)

## 难点 1：数据不丢（断网/断电/服务崩溃）

**现象**：现场网络抖动、网关断电、broker 重启，数据丢一段。
**为什么难**：端到端链路有 4 个可能丢数据的环节（设备→网关、网关→broker、broker→平台、平台→存储），任何一环断都丢。
**应对策略**（本仓库已体现 2 层，生产共 4 层兜底）：

| 层 | 策略 | 本仓库实现 |
|---|---|---|
| L1 边缘缓存 | 网关本地缓存，重连补报 | `gateway.js` SQLite 缓存 ✅ |
| L2 传输保证 | QoS 1 + 持久会话 | `publisher.js` qos:1 + clean:false ✅ |
| L3 消费暂存 | 平台写库失败暂存重试 | `tsdb-sink.js` pending 表 ✅ |
| L4 对账兜底 | 定期对账（设备侧计数 vs 平台计数），差异补拉 | 生产需补 |

> 生产补强：L1 缓存要设**容量上限**（如 10 万条），防止断网一天把网关存储写爆；补报要**限速**（如每秒 200 条），防止恢复瞬间压垮 broker 和平台。

## 难点 2：消息重复（QoS 1 的代价）

**现象**：QoS 1 保证"至少一次"，网络重传/重连补发导致同一条数据到达多次。
**应对策略**：
- **平台幂等**：`deviceId + ts`（或设备递增序号）唯一键去重——本仓库 `subscriber.js` 已实现 ✅
- **生产升级**：去重表用数据库唯一索引（如 TDengine 按 ts 主键天然去重；MySQL 用 UNIQUE KEY），不依赖内存窗口（内存窗口重启失效）
- **关键认知**：让"重复"在业务上无害，而不是消灭重复（消灭重复代价极高，QoS 2 慢且重）

## 难点 3：数据乱序与延迟

**现象**：网络抖动导致后发的数据先到；设备时钟不准导致时间戳错乱。
**应对策略**：
- **排序键**：数据带"设备时间 + 设备递增序号"，消费端按 (deviceId, seq) 排序，不依赖到达顺序
- **时间戳选择**：业务分析用"设备时间"（数据产生时刻），平台接收用"服务器时间"（记录到达），两列都存，别混
- **容忍窗口**：入库允许 5 分钟乱序窗口（时序库特性），超出窗口按异常标记

## 难点 4：海量连接（10 万级设备在线）

**现象**：设备多了，单 broker 连接数、心跳流量、内存暴涨。
**应对策略**：
- **Broker 选型**：EMQX（单节点百万连接）替代 Mosquitto（万级）
- **心跳优化**：心跳间隔调到 60-120s；利用 MQTT 特性（Keep Alive + LWT 遗嘱）代替应用层心跳
- **连接配额**：每台网关代理 N 台设备（一台网关 = 一条连接），减少连接数 1-2 个数量级
- **分级接入**：区域接入层（每车间一个 broker）→ 汇聚层

## 难点 5：时序数据存储膨胀

**现象**：1 秒 1 条 × 10 万设备 = 每天 86 亿条，磁盘和查询都扛不住。
**应对策略**：
- **时序库**：TDengine/InfluxDB（列式 + 压缩 + 时间分区），本仓库已用 TDengine ✅
- **降采样**：连续查询把 1s 原始数据聚合成 1min/1h 表，历史分析查聚合表
- **保留策略**：原始数据 TTL 30 天，聚合数据保留 2 年，冷数据归档对象存储
- **写入批量化**：sink 攒批（5 秒或 1000 条一提交），写入吞吐提升 10 倍+

## 难点 6：设备协议碎片化

**现象**：Modbus、OPC UA、西门子 S7、三菱 MELSEC、私有协议……每种设备一套"方言"。
**应对策略**：
- **边缘网关收编**：网关做协议转换，平台只认 MQTT 标准格式（本仓库 `gateway.js` 正是此模式 ✅）
- **协议适配层**：网关内建"驱动"体系（一个协议一个驱动模块），新协议 = 加驱动
- **统一数据模型**：所有设备归一化为 `{deviceId, ts, 指标键值...}`，平台不感知底层协议
- **选型策略**：优先支持 Modbus（90% 仪表）+ OPC UA（新设备趋势），私有协议遇到再写驱动

## 难点 7：下行指令可靠（控制类）

**现象**：平台发"停机"指令，设备没收到或执行了但平台不知道。
**应对策略**（本仓库 `device.js`/`control.js` 已完整实现 ✅）：
- **msgId 配对**：指令带唯一 ID，设备执行后 ack 回传同一 ID——本仓库已实现
- **超时重试**：5s 无 ack 标记失败/重发（`control.js` 已实现超时，生产加重试上限 + 退避）
- **指令幂等**：同一 msgId 重复执行无副作用（设备侧按 msgId 去重）
- **指令过期**：带 expire 时间戳，设备收到过期指令直接丢弃（防"迟到的旧指令"）
- **分级指令**：控制类（需 ack）与配置类（尽力而为）分开主题

## 难点 8：安全（伪造/窃听/越权）

**现象**：公网部署后，有人伪造设备上报、窃听数据、冒充平台下发指令。
**应对策略**：
- **传输层**：TLS 加密（证书双向认证，设备有私钥，broker 验设备证书）
- **设备身份**：一机一证书 + 证书吊销列表；不用共享密码
- **主题权限**：EMQX ACL——设备只能发 `devices/{id}/up`、订阅 `devices/{id}/down`，互不可见
- **数据完整性**：payload 带 HMAC 签名（设备密钥），平台验签防篡改
- **平台侧**：REST API 加鉴权 + 限流，管理操作全审计

## 难点 9：断网恢复时的"缓存风暴"

**现象**：网络恢复瞬间，所有离线网关同时补报，broker/平台被瞬间打爆。
**应对策略**：
- **补报限速**：网关补报限速（每秒 N 条），并设单次补报上限（如先补最近 1 小时）
- **错峰**：网关补报加随机延迟（0-60s），避免同时
- **平台削峰**：接入层限流 + 消费端批量写库
- **优先级**：先补"状态类"（当前值），历史数据异步慢补

## 难点 10：网关配置与运维（批量管理）

**现象**：1000 台网关，每台采集频率/上报地址不同，改配置要一台台去现场。
**应对策略**：
- **配置云端下发**：网关启动拉取配置（HTTP/MQTT），配置变更通过指令通道下发（本仓库指令通道可扩展）
- **配置版本化**：配置带版本号，网关校验，防止旧配置回退
- **远程运维**：远程日志拉取、远程重启（指令通道）、OTA 升级（A/B 分区防变砖）
- **分组管理**：按产线/车间分组下发配置

## 难点 11：可观测性缺失（系统黑盒）

**现象**：设备数据突然中断，不知道是设备挂了、网关挂了、网络断了还是 broker 挂了。
**应对策略**：
- **链路分层监控**：每层上报心跳（设备→网关心跳、网关→平台心跳、sink→库心跳），任一层断都能定位
- **关键指标**：设备在线率、上报延迟（设备时间 vs 平台接收时间）、消息积压数、入库失败率
- **LWT 遗嘱消息**：设备异常掉线 broker 自动广播"设备离线"事件（MQTT 原生特性，本仓库未演示，生产必用）
- **告警收敛**：先告警"根因"（如网关离线），不告警一堆"果"（该网关下所有设备离线）

## 难点 12：成本控制（带宽/存储/算力）

**现象**：数据量上来后，4G 流量费、存储成本、云资源费失控。
**应对策略**：
- **边缘计算**：网关本地聚合（1s 原始 → 30s 平均再上报），流量降 30 倍
- **变化上报**：数值变化超过阈值才上报（死值不报）
- **存储分层**：热/温/冷分级，冷数据压缩归档
- **压缩选型**：TDengine 默认压缩率 10:1+，远优于 MySQL
